# v1 利用シーンとスコープ

- 状態: decided
- 作成日: 2026-09-06
- 最終更新日: 2026-09-06
- 関連: `doc/design/concept.md`

## 背景

実装に入る前に、誰が何のために使うかと、v1 で公式に公開する判定の範囲を固定する必要がある。ここが決まらないと CLI の exit code、次点機能の公開有無、会社カレンダー対応の境界がぶれる。

## 候補

- A: 主用途を cron / シェルのゲートとし、v1 公開機能は月の最初 / 最後の業務日判定のみに絞る
- B: 主用途を人間の対話確認とし、業務日 / 休日判定も v1 の公開 CLI に含める
- C: 会社固有休日や翌営業日・営業日数まで v1 に含める

## 検討内容

主目的は既に「その月の最初 / 最後の業務日か」である。ゲート用途なら `bizdate --last && monthly-job` のように exit で分岐でき、対話 UI は不要である。

業務日判定そのものは first / last 判定の内部実装として必須だが、公開 CLI に出すと option と exit 契約が増え、初期スコープが広がる。会社カレンダーや営業日演算は需要はあるが、データ源・設定方式が別テーマになり、v1 のブロッカーではない。

対象カレンダーを日本以外に広げると祝日データの正本と更新方針が複雑になる。コンセプトも当面は日本の祝日を扱う前提である。ただし将来の他国対応を否定する意図はなく、v1 では対象外に留める。

## 決定

- 主用途は cron / シェルのゲートとする。人間の確認は副次とし、対話 UI は持たない
- v1 の対象カレンダーは日本の国民の祝日のみとする。他国は v1 対象外とする
- 日本以外の祝日への対応は将来の拡張候補として残す。時期・対象国・データ源は未決とする
- v1 の公開機能は「指定日がその月の最初の業務日か」「最後の業務日か」だけとする
- 業務日判定ロジックは内部実装として必須だが、業務日 / 休日判定モードは v1 の公開 CLI に含めない
- 会社固有休日、翌 / 前営業日、第 N 営業日、営業日数は v1 対象外とする

## 理由

主目的に対して最小の公開面でゲート用途を満たせ、後から公開 CLI・会社カレンダー・他国祝日を足しても契約を壊しにくいため。他国対応は意図として残すが、v1 のブロッカーにはしない。

## 影響

- `concept.md` の v1 スコープと次点候補を更新する
- CLI は predicate（該当 / 非該当）を中心に設計する
- 会社カレンダーや多国対応の仕様・設定ファイルは当面置かない
- 実装の祝日データ層は、将来の国・カレンダー差し替えを妨げない程度の分離を意識してよい（必須の抽象化までは求めない）

## 後から見直す条件

- ゲート以外の対話確認が主用途になった場合
- 業務日 / 休日判定を公開 CLI に出す需要が明確になった場合
- 会社カレンダー対応が必須になった場合
- 特定国の祝日対応を着手する時期が決まった場合

## 追記 (2026-09-06)

業務日定義（0005）の合意に伴い、会社固有休日の境界を次のように明確化する。

- v1 対象外のままなのは、埋め込みの会社カレンダーや設定ファイルによる休日集合である
- CLI option `--day-off` による日付リストの利用者指定休日は v1 対象とする。詳細は [0005](0005-business-day-definition.md)
- option 既定をコンフィグファイルで上書きする構想は将来候補とし、v1 には含めない

## 追記 (2026-09-06) 祝日データの取得方式

祝日データ方針（0006）の合意に伴い、v1 の公開面を次のように補足する。

- 判定用の公開機能に加え、祝日データをネット取得してローカル保存するサブコマンドを v1 に含める
- 判定コマンド自体はネット取得しない。ローカル欠落・期限切れはエラーとする
- 他国祝日の将来対応は、取得先 `--source` に任意 CSV URL を渡す想定とする。詳細は [0006](0006-holiday-data-source.md)
