# review metadata の位置と Model の確認手段

- 状態: decided
- 作成日: 2026-09-24
- 最終更新日: 2026-09-24
- 関連: `.agents/skills/review-pull-request/SKILL.md`, `.agents/skills/drive-issue-to-reviewed-pr/SKILL.md`, `doc/guidelines/cloud-session-guidelines.md`, `doc/guidelines/github-mcp-guidelines.md`, `doc/design/decision-log/0018-cloud-session-environment.md`, `doc/design/decision-log/0019-issue-review-cycle-orchestration.md`, `doc/design/decision-log/0023-model-identifier-scope.md`

## 背景

PR #67（Issue #64）の review cycle を cloud session で回したところ、`review-pull-request` の canonical metadata が規定どおりにならなかった（Issue #69）。5 行そのものは書き込めており、投稿後に削られてもいなかった。規定から外れたのは次の 2 点である。

- 位置: cloud session の harness は、GitHub へのすべての投稿の末尾を footer（`---` と「Generated by Claude Code」の行）にするよう agent に求め、付けなければ server が付ける。skill は「投稿の末尾に 5 行を置く」と定めており、footer が付く環境では文字どおりには満たせない。末尾の行から読む parse も外れる。
- `Model`: 投稿によって `unknown` と識別子に分かれた。記載してよい範囲は 0023 で決めたが、確認の手段は決めず #69 に送っていた。skill は「実行環境から確認する」とだけ書き、cloud session での手段を示していなかった。

あわせて、投稿後に誤りに気付いても直す手順が無かった。MCP tool は conversation comment を編集できるが、inline comment とその返信、提出済み review の本文は編集できない。#70（0018 の追記）で cloud session に `gh` が入り、`gh api`（REST）で編集できるようになった。

## 候補

位置と parse:

- A: 「投稿の最終行から 5 行」を保ち、footer を付けないよう agent に求める。
- B: 「投稿の末尾。footer が付く場合はその直前」とし、parse は位置ではなく 5 つのキーの並びで行う。

`Model` の確認手段:

- C: 実行環境によらず、system prompt が示す識別子だけを使う。
- D: cloud session の session 本体は `get_session` の値を使い、subagent は自身の system prompt が示す識別子を使う。
- E: orchestrator が確認した値を brief で subagent に渡す。

誤りの訂正:

- F: 訂正の投稿を追加する。
- G: その投稿を編集する。手段が無ければ人間に依頼する。

## 検討内容

- A: footer は harness の指示で、付けなければ server が付ける。repository のルールでは止められず、Issue のスコープ外でもある。
- B: footer の有無と内容に依存しない。footer が付かない環境（ローカルの Claude Code、Codex、Cursor）では、footer の直前という条件が消えるだけで、これまでと同じ書き方になる。5 行と footer の間に空行が無いと、`---` の直前の行（`Mode`）が Markdown の見出し（setext heading）として表示されるため、空行を 1 行置く。キーの並びで探すため、1 投稿に 2 組あると特定できない。1 投稿 1 組とし、他の投稿の metadata を行ごと引用しないことにする。
- C: cloud session の system prompt は、model を答えるときに `get_session` で確かめるよう求めている。設定された model と実際に応答した model は fallback などで異なり得るとも述べている。system prompt の記載だけでは実際に応答した model を表さない場合がある。
- D: `get_session` の `external_metadata.last_served_model` は実際に応答した model を表す。一方で `get_session` が示すのは session の model であり、subagent が別の model で起動されている場合がある。2026-09-24 に cloud session の subagent で確かめたところ、subagent の system prompt には exact model ID の行があり、`get_session` も呼べた（値は session と同じ）。subagent は自身の system prompt を使えば、自分の model を書ける。
- E: PR #67 では orchestrator が subagent に `unknown` を指示し、投稿者によって値が分かれた。確認していない値を写すことになり、記録として使えない。
- F: 1 投稿 1 組と、完了要約 1 本の前提が崩れる。どちらの組が正しいかを parse で決められない。
- G: MCP で編集できる conversation comment は MCP を使い、編集できないものは `gh api` で補う。0018 と `doc/guidelines/github-mcp-guidelines.md` の「`gh` で補う範囲」が、同じ Agent 種別の投稿の編集を agent に許している。削除は `doc/guidelines/github-cli-guidelines.md` でユーザーの承認が要るため、削除と再投稿は選ばない。

## 決定

- 位置は B とする。投稿の末尾に置き、実行環境が footer を付ける（または付けるよう求める）場合はその直前に置く。footer を自分で書く場合は間に空行を 1 行置く。footer を書くよう求められていない agent（cloud session の subagent など）は 5 行で投稿を終え、実行環境が付けた footer との間の空行を read-back で確かめる。parse は 5 つのキーがこの順で連続する 5 行で行う。1 投稿に 1 組とする。
- `Model` の確認手段は D とする。cloud session の session 本体は `get_session`（`session_id` を省略）の `external_metadata.last_served_model` を書き、無い場合は `session_context.model` を書く。subagent は自身の system prompt が示す識別子を書く。それ以外の環境では、実行環境が示す識別子を書く。書くのは exact model ID（`get_session` の値と同じ形）とし、表示名は書かない。`get_session` は投稿の直前に呼ぶ。確認できない場合は `unknown` とする（0023）。
- 委譲する側は `Model` の値と、skill と異なる書き方を指示しない（E を採らない）。`drive-issue-to-reviewed-pr` の委譲 brief にこれを明記する。
- 投稿の前に、キーの並びと位置、`Agent` と `Model` の確認元、`Review cycle`、投稿直前に取り直した head SHA、`Mode` を確かめる。
- 誤りの訂正は G とする。conversation comment は MCP の `update_issue_comment`（ローカルの `github-op-integrated` は allowlist に無いため `gh api`）、inline comment とその返信、提出済み review の本文は `gh api` で編集する。`gh` が使えない場合と、誤りが `Agent` 行にあるなどで同じ Agent 種別の投稿だと確認できない場合は、対象と正しい値を報告して人間に GitHub の UI での編集を依頼する。subagent は note を書かず、報告を orchestrator へ返す。
- 正本は `.agents/skills/review-pull-request/SKILL.md` の「可視 metadata の canonical フォーマット」とその下の 2 節とする。cloud session 固有の事情は `doc/guidelines/cloud-session-guidelines.md` の「なぜ専用の設定が要るか」に 1 行置き、skill を参照する。

## 理由

footer は repository のルールの外で付くため、規定の側を footer に合わせる。位置ではなくキーの並びで読むことで、footer の形が変わっても parse が外れない。`Model` は記録として揃うことに意味があり（0023）、揃えるには投稿する Agent がそれぞれ同じ規則で自分の値を確かめる必要がある。誤りを編集で直すことで、1 投稿 1 組の前提を保てる。

## 影響

- `.agents/skills/review-pull-request/SKILL.md` の「可視 metadata の canonical フォーマット」を改め、「`Model` の確認手段」と「投稿前の確認と誤りの訂正」を加えた。
- `.agents/skills/drive-issue-to-reviewed-pr/SKILL.md` の「subagent への委譲」に、metadata の値と書き方を brief で指示しないことを加え、brief の形に 1 行足した。
- `doc/guidelines/cloud-session-guidelines.md` の「なぜ専用の設定が要るか」に 1 行加えた。`doc/guidelines/github-mcp-guidelines.md` は、tool routing の正本として「操作別の第一選択」に comment / review 本文の編集の行（環境ごとの手段と、編集してよい投稿の制約）を足し、「`gh` で補う範囲」の編集の行に metadata の訂正に使う旨を加えた。
- 0023 は確認の手段を #69 に送っていたため、本ログを参照する追記を置いた。
- `.github/copilot-instructions.md` と入口 shim は同期しない。どちらも review metadata の書き方を扱っていない。

## 後から見直す条件

- harness の footer の形が変わり、キーの並びでは 5 行を特定できなくなったとき。
- `get_session` の field 名や意味が変わったとき、または subagent の system prompt が model の識別子を示さなくなったとき。
- MCP tool に review comment や review の本文を編集する手段が加わり、`gh api` に頼る必要がなくなったとき。
