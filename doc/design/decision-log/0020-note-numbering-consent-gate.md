# 採番 skill における完了タスク行の合意ゲート

- 状態: decided
- 作成日: 2026-09-13
- 最終更新日: 2026-09-13
- 関連: `.agents/skills/number-working-branch-note/SKILL.md`, `doc/guidelines/working-branch-notes-handling.md`, [0019-issue-review-cycle-orchestration.md](0019-issue-review-cycle-orchestration.md), Issue #52, PR #44 / PR #46 / PR #51

## 背景

`number-working-branch-note` は、note 本文（Step 5）と PR description（Step 10）に残る**完了タスク行**を書き換える際、置換候補を提示してユーザー合意を得ることを要求していた。このゲートは PR #44 で導入され、PR #46 で維持された。由来は「本 skill は定型だけを機械置換する設計であり、判断を要する完了タスク行はその外側の手順として分ける」である。

PR #51 で orchestrator skill `drive-issue-to-reviewed-pr`（0019）を追加し、その PR 自身へ自己適用したときに、このゲートへ実際に当たった。採番は PR 作成直後に必ず通る経路であるため、ゲートが残る限り orchestrated flow の P1 の途中で人間の手番が毎回 1 回入る。

本ログは「作業メモへの書き換えに合意が要るか」だけを扱う。1Password の承認ダイアログを避ける目的で git 操作の前段に置くゲートは由来が別であり、対象としない。

## 候補

- **A**: 機械的に判定できる完了タスク行（本 skill の終了時点で未完のまま残らず、完了要素と未完了要素が混在しない行）は合意無しで書き換える。合意を要求する範囲を複合行と判断不能な行だけに絞る。
- **B**: 合意ゲートを廃し、判定できる行は書き換え、判定できない行は触らず終了時に報告する。
- **C**: 現状維持とし、代わりに orchestrator（`drive-issue-to-reviewed-pr` の「停止とエスカレーション」）にゲートの存在を明記する。

## 検討内容

- 判定はすでに skill 内で機械化されている。PR #46 で「本 skill の終了時点で未完のまま残るか」という判定基準と、複合行・判断不能な行は触らず報告するという切り分けを明文化した。ゲートが導入時に守っていた「判断を要する行」は、この明文化によって skill 内で処置が決まっている。
- note は最終仕様書ではなく作業メモであり、整合性のスコープは「当ブランチの作業判断・経緯を読める範囲で十分」と定めている（`doc/guidelines/working-branch-notes-handling.md` の「整合性のスコープ」「メンテコスト判断」）。書き換え形式は checkbox を `- [x]` にするか行末へ `（完了）` を付す付記に限られ、行は削除しない。この基準に照らして低リスクかつ可逆である。
- A は、合意を残す実質的な対象が無い。複合行と判断不能な行は PR #46 の時点で「触らず、終了時に報告する」と定めた行であり、A を採ると「書き換えない」と決めた行に合意経路を新設することになって Step 5 の既存規定と衝突する。
- C は、ゲートを残す根拠が由来側で解消済みである点に答えていない。orchestrator へ転記しても、頻度の高い人間の手番はそのまま残り、同じ規定が 2 箇所に増える。
- 合意を廃すと、ユーザーが書き換えを知る経路が無くなる。B ではこれを「終了時の報告」で担保し、書き換えた行の一覧を報告項目へ加える。
- 誤検出のコストは、「ユーザーが提示された候補を却下する」運用（PR #44 のリスク欄）から、「報告を読み、必要なら後から直す」運用へ移る。付記のみの可逆な変更であるため受け入れる。

## 決定

案 B を採用し、PR #44 / PR #46 で維持した合意ゲートを撤回する。

- 機械判定できる完了タスク行は、ユーザー合意を待たず書き換える（Step 5 / Step 10）。
- 判定基準と、複合行・判断不能な行を触らない切り分けは PR #46 のまま変えない。
- 「終了時の報告」に、完了として書き換えた行の一覧を加える。
- 「やらないこと」を、触らない対象（定型外の stale 表現、複合行、判断不能な行、title）の列挙と、機械判定できる行の書き換えで処理を止めないことの両方へ揃える。
- `drive-issue-to-reviewed-pr` 側にゲートの記述は追加しない。

あわせて、同種の合意ゲート（成果物の内容判断を理由とするもの）が他 skill に無いことを確認した。`maintain-progress` の「判断に迷う箇所は止めてユーザーに確認する」は判断不能な場面の安全弁であり、機械判定できる出力にまで合意を要求するものではない。`review-pull-request` / `run-issue-task` / `register-progress-issue` / `drive-issue-to-reviewed-pr` の停止条件は、入力の曖昧性や前提条件の不成立に対するものである。いずれも本決定の対象外とし、別 Issue へ切らない。

## 理由

ゲートの由来は「判断を要する行を機械置換の外側へ分ける」ことであり、その判断は PR #46 の判定基準の明文化によって skill 内へ取り込まれた。残る判断不能な領域は、ゲートではなく「触らず報告する」で既に閉じている。すなわちゲートは、合意を必要としない行だけを止めている。

書き換えの影響は作業メモへの付記に限られ、note の整合性スコープに照らして低リスク・可逆である。一方でゲートの費用は、必ず通る経路に毎回発生する人間の手番であり、orchestrated flow の自律性を恒常的に損なう。費用が便益を上回る。

## 影響

- `.agents/skills/number-working-branch-note/SKILL.md`: 「stale 表現の定型置換」の前置き、「手順」の前置き、Step 5、Step 10、「終了時の報告」、「やらないこと」を揃えた。frontmatter の `description` は変更しない（skill の責務は変わらない）。
- `drive-issue-to-reviewed-pr` の P1 が人間の手番なしに通るようになる。Issue #52 の PR 自身の採番を、その最初の実行例として扱った。
- `doc/guidelines/` に変更は無い。ゲートは skill の手順にのみ存在していた。
- 他 skill の手順に変更は無い。
- 誤検出の可視化は「終了時の報告」に依存する。報告を省いた実行は、この決定の前提を欠く。

## 後から見直す条件

- 誤検出の書き換えが実運用で繰り返し発生し、報告経由の事後修正では収まらなくなったとき。
- 判定基準を緩めて、書き換え対象を「本 skill の終了時点で未完のまま残るか」より広い範囲へ拡張するとき。判定の確実性が下がるため、ゲートまたは別の安全弁の要否を再検討する。
- 書き換え形式に、行の削除や文意の再構成のような不可逆な操作を含めるとき。
