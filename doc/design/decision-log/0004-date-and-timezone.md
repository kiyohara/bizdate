# 日付とタイムゾーン

- 状態: decided
- 作成日: 2026-09-06
- 最終更新日: 2026-09-06
- 関連: `doc/design/business-day.md`, `doc/design/cli-interface.md`

## 背景

「今日」と「その月」の境界を固定しないと、UTC の cron / CI や時刻付き入力で日付が1日ずれ、業務日判定が誤る。祝日定義より先に決める必要がある。

## 候補

- A: カレンダー日付のみを扱い、入力は `YYYY-MM-DD`、省略時の「今日」は常に `Asia/Tokyo`
- B: 実行環境の local timezone を「今日」に使う
- C: slapex と同様に `/` 区切りや時刻付き入力も広く受け付ける
- D（採用寄り）: A をベースにしつつ、「今日」の既定は local timezone とし、タイムゾーンは環境変数または CLI option で上書き可能にする

## 検討内容

カレンダー日付のみ・入力は `YYYY-MM-DD`・範囲外はエラー、という A の骨格はゲート用途に合う。

一方、常に `Asia/Tokyo` 固定だと、利用者が別タイムゾーンで「その地の今日」を見たい場合に不便である。既定を local timezone にすれば、普段は環境の暦日で動き、日本の暦日が欲しいときはタイムゾーン指定で合わせられる。

タイムゾーン指定の経路は、環境変数（cron / CI で引き回しやすい）と CLI option（一時上書き）の両方がある方が実務に合う。優先順位は明示しておく必要がある。

時刻付き入力や広い日付形式は v1 の価値に寄与しにくい。祝日データ範囲外を土日だけで成功させると静かに誤判定する。

## 決定

- カレンダー日付だけを見る。時刻は扱わない
- 「その月」は指定日が属する暦月とする
- 日付入力は `YYYY-MM-DD` のみとする
- 日付省略時の「今日」は、採用するタイムゾーンにおける暦日とする
- タイムゾーンの既定は、実行環境の local timezone とする
- タイムゾーンは上書き可能とする。指定経路は次の両方を提供する
  - 環境変数 `BIZDATE_TZ`（IANA 名、例: `Asia/Tokyo`）
  - CLI option `--timezone`（同じ形式）
- 優先順位は `--timezone` > `BIZDATE_TZ` > local timezone とする
- 不正な日付、未知のタイムゾーン、および祝日データ保証範囲外の日付は推測せずエラーとする
- プロセス全体の `TZ` 環境変数を、bizdate 専用の指定手段としては採用しない（local timezone の解釈には OS / ランタイムの通常規則が効いてよい）

## 理由

A の単純さを保ちつつ、既定を local にし上書き経路を二つ用意すると、日常利用と cron / CI の両方で「どの暦日の今日か」を制御できるため。

## 影響

- 業務日仕様に日付・タイムゾーン節を置く
- CLI 仕様に `--timezone` と `BIZDATE_TZ` を載せる（詳細は CLI テーマでも確認する）
- 範囲外日付・不正タイムゾーンは exit code で失敗扱いとする（詳細は CLI 方針）

## 後から見直す条件

- `TZ` 自体を公式の指定手段に含めた方がよいという運用要求が出た場合
- 時刻付き入力や他形式の日付を受け付ける必要が出た場合
- オフセット固定（`+09:00`）指定の需要が出た場合
